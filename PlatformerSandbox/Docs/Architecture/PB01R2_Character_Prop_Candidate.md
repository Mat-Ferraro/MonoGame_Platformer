# PB01-R2 — Kinematic character / prop interaction candidate

Baseline: user-accepted PB01-R1/R2 Prop Contacts Candidate (including Micro-Bounce Fix). Apply this overlay at solution root. All source files are complete replacements; no project file changes.

## Implemented scope

A staged, conservative coupling approach. At the beginning of a fixed tick, construct an immutable collider view from authored terrain and eligible dynamic-body start bounds. On the staged character motor, refresh this view and the existing analytical jump motor's collider view. The existing motor remains authoritative for character acceleration, jump trajectory, support and collision response; no character mass or force-driven movement. Ground support is refreshed when geometry changes. At the accepted character endpoint, horizontal intent against an actual touching prop face supplies a bounded force (default 120 world force units; zero disables pushing). The prop solver advances all props against terrain, other props and the final live character bounds as fixed, zero-restitution, zero-friction boundaries. Push forces are staged, not written into committed pending forces. The existing chronological prop solver commits only after successful nonpenetrating integration. This is not a single continuous timeline shared by characters and props. No body or player teleporting is used to resolve ordinary contacts.

## Configuration and validation levels

Body mask `Terrain, Dynamic, Character` opts into character collisions. Existing other authored worlds without that bit retain prior behavior. All 8 and 11 fixtures in Physics Interaction Lab and Engine Integration Lab opt in. Spawned wood crates also opt in. Physics lab body 3 moved away from the authored spawn; integration body 1 rests near spawn (x=11.5, y=24.5). Both initial spawn and terrain intersection checks pass. `CHARACTER COLLISION` can be toggled per prop; re-enabling when overlapping any committed live character is rejected. Spawn/reset operations are validated against live character bounds. `CHARACTER PUSH FORCE` has selections 0,30,60,120,240. Setting 0 keeps characters solid but prevents their walking intent from applying push forces. Character push requests count per body per tick, not successful movement; boundary impacts count actual prop-solver collisions against live characters. Stable prop adapter ID is int.MaxValue minus body local ID; conflicts with authored collider IDs are explicitly rejected. Prop IDs and other entity identities remain typed in physical snapshots.

## Limitations / open requirements

The split phases freeze prop geometry during character movement and character endpoints during prop motion; this deliberately does not implement simultaneous relative character/prop CCD, exact continuous pushing or moving support transport, character weight, impact displacement/knockback, character/character or NPC collisions, platform/prop transport, coupled compression or general crush response inheritance. A moving platform can classify a crush against a temporarily fixed crate even where a full coupled solve could permit escape; mixed-motion situations require the future unified solver. Existing crush recovery still handles classified character crushes. Per-character prop ghost pairs, automatic stop/reverse, object destruction, full LDtk entity schema and dynamic shadows remain outstanding. The adapter is a limited, opt-in functional step, not PB01 completion. Do not use it as evidence that the entire contact-island design is implemented.
